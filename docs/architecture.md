# 架构与实现边界

## 平台决策

首期面向 XF40H 上的 ArkOS + PortMaster，编译目标暂定 aarch64。
设备资料与方屏方案见 [XF40H](devices/xf40h.md)。在实际固件确认后固定交叉编译环境、
最低系统依赖版本及真机测试配置。其他固件和 armhf 可以随后添加，不在未经测试时声明兼容。

选择 C + SDL2 + CMake，沿用原作 C 逻辑，并通过 SDL2 提供显示和输入。
渲染优先采用 SDL_Renderer，保留软件渲染可用性；不把桌面 OpenGL 或 X11 作为必须依赖。
显示后端的实际支持仍须在 ArkOS 目标机上验证。

原作两代都提供 Linux 版本和源码，一代已有 SDL 掌机移植参考。
已有移植用于对照显示和输入处理；两代游戏规则以选定版本的原作为基准。

## 两个程序，共享平台代码

计划构建以下目标：

| 目标 | 来源 | 职责 |
| --- | --- | --- |
| `promesst` | `build/<目标>/generated/promesst/` | 一代游戏循环、规则、地图、撤销与存档格式 |
| `promesst2` | `build/<目标>/generated/promesst2/` | 二代游戏循环、规则、地图、撤销与存档格式 |
| `handheld_platform` | `src/platform/` | 供两代链接的平台适配代码 |

两个可执行程序拥有独立进程和游戏状态。首期不用一套通用规则引擎承载两代，
也不要求把原作单文件立即拆成大量模块。先保留可追溯的规则代码，再逐步抽出平台调用。

依赖方向为：游戏代码调用平台接口；平台代码不依赖地图、光线规则或某代的存档结构。
共享平台库可以静态链接到两个程序，玩家安装任意一代不需要安装另一代。

## 源码和资源的来源

`upstream/` 保存各自从官网下载的固定版本快照。
修改保存在适配脚本及 `src/platform/`，通过 SHA-256 和原作状态轨迹对照追踪变化。原始快照不提交到 Git。构建使用 `scripts/prepare_sources.py` 将原作生成到被忽略的 `build/<目标>/generated/`，并链接本项目共享平台代码。当前 `src/games/` 为预留目录。

`assets/` 保存实际发布的资源。尽量沿用原始素材，只有需要转换或增加掌机按键提示时才生成新文件。
资源转换需可重复，并记录输入来源和输出格式。游戏内部原本嵌入源码的地图可以继续嵌入。

## 平台接口的范围

`src/platform/sdl2/`：

- SDL 初始化与释放、全屏显示、视口缩放、像素滤镜设置。
- 将键盘和掌机输入转换为游戏动作，处理菜单导航、按下边沿和重复输入。
- 提供时钟及帧调度，保持原作与时间相关的行为。
- 处理正常退出、控制器断开及恢复。

`src/platform/storage/`：

- 读取明确的资源、存档、配置目录，桌面与掌机使用同一约定。
- 创建运行数据目录并提供可靠的文件写入辅助。
- 存档格式仍由各代游戏负责；新格式若有必要，明确版本号和迁移策略。

首期资源、存档、配置路径约定分别为 `PROMESST_ASSET_DIR`、`PROMESST_SAVE_DIR`、
`PROMESST_CONFIG_DIR`，两代均可读取。它们是本项目计划实现的接口，原作目前并不支持这些变量。
桌面默认路径应与掌机一致地区分两款游戏。

## 操作与显示

默认操作按实体按键位置定义，避免不同设备 A/B 字母布局造成误会。

| 实体按键 | 拟定动作 |
| --- | --- |
| 方向键 | 移动 / 菜单导航 |
| 下方动作键 | 对应原作 Z 动作；菜单确认 |
| 右方动作键 | 对应原作 X 动作；菜单返回 |
| R1 | 对应原作 Backspace 撤销 |
| Start | 打开原作菜单，提供继续、重开、检查点、署名和保存退出 |
| 左方动作键 | 二代原作 C 动作 |
| 上方动作键 | 切换缩放方式 |

各代的具体动作和撤销粒度以原作为准。例如已查看的一代实现按房间记录撤销，
不能未经说明改成逐步撤销。动作解锁时机和界面说明也必须保留。
移动可使用经过验证的延迟重复；动作键和撤销键默认每次按下触发一次。
正常退出由游戏负责保存；PortMaster 强制退出快捷键仅作为异常退出通道。

以原作逻辑画布为基础保持比例；整数缩放优先，无法整数放大时允许最近邻等比缩放。
不同宽高比留边，不拉伸或裁切关键信息。优先验证 XF40H 的 720×720，再检查 640×480 和 480×320。
二代逻辑画布尺寸在导入源码后确认。

## 实施顺序

先实现一代桌面版本，之后完成一代真机安装包，再接入二代。
共享平台接口从一代实际需求中抽取；二代接入时只合并确实相同的平台行为。
GBA 作为后续独立后端评估，本阶段不创建 GBA 工具链或发布目标。
